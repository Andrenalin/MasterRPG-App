## 3. Concurrency

### 3.1 Pervasive, redundant `MainActor.run` hopping in the SharePlay/network hot path — NOW FIXED
- **Location:** `Modules/GameRPG/Controller/PlayerController.swift` — 54 sites (1122, 1148, 1181, 1207, 1240, 1266, 1325, 1329, 1381, 1384, 1433, 1436, 1543, 1813, 2075, 2079, 2085, 2088, 2601, 2750, 2761, 2792, 2795, 2975, 3008, 3041, 3100, 3113, 3145, 3176, 3197, 3222, 3226, 3292, 3327, 3349, 3375, 3385, 3444, 3488, 3527, 3556, 3575, 3580, 3599, 3638, 3701, 3716, 3722, 3732, 3743, 3751, 3758, 3770); `Modules/GameRPG/Controller/MasterController.swift` — 6 sites (521, 547, 622, 754, 1141, 1577); ~~`Modules/GameRPG/Network/GameNetworkController.swift` — 1 site (786)~~ **FIXED** as a side effect of the §3.2 pass (`sendData` is itself `@MainActor` + `@discardableResult`; `await` alone hops there now).
- **What:** `PlayerController` and `MasterController` are plain `final class ... : Sendable` (not `@MainActor`, not an actor) holding an `@MainActor @Observable` model. Nearly every read/write of that model's state wrapped in `await MainActor.run { ... }` instead of directly `await`-ing the already-`@MainActor` property/method — e.g. the model already defined `setGameUpdateType(_:)` at `PlayerController.swift:966-968`, but most call sites bypassed it in favor of a closure.
- **Why:** This is the busiest concurrency-critical subsystem in the app (network I/O feeding UI state). The redundant hops added scheduling overhead per message, obscured which reads are genuinely atomic multi-field snapshots versus simple single-field mutations that don't need a closure, and made the real isolation boundary harder to audit at a glance.
- **Fix:** All 60 sites across both files were individually read and converted using one of four patterns:
  - **Calling an already-`@MainActor` method, or a single property read/call** → drop the wrapper; `await` alone hops there (e.g. `await root.gameModel.outgoingMessage(...)`, `await root.gameModel.gameTableModel?.syncPawnsWithMapPins()`).
  - **A single property write** → route through the model's existing `setGameUpdateType(_:)` mutator, or a new same-shaped one added for this pass. Swift disallows forming a key path to an actor-isolated stored property at all (confirmed the hard way — see the self-correction below), so the 4 `pending*Requests`/`requested*RepairIds` `Set<UUID>` properties each got 2 named insert/remove mutators (`insertPendingAudioRequest`/`removePendingAudioRequest`, and the `RequestedRepairId`/`RequestedPdfRepairId`/`RequestedSpaceRepairId` equivalents) instead of one generic keypath-based helper.
  - **Multiple statements that must land as one atomic MainActor unit** (a genuine write-write or read-then-write race the audit itself was right to flag) — extracted a dedicated `@MainActor` method: on `PlayerControllerModel` when it only touches that model (`resetForLostConnection(preservingSharePlayRebind:)`, `clearGameUpdateTypeIfPhoto()`, `completePdfRepairAndSetUpdateType(_:)`), or on `PlayerController`/`MasterController` when it spans two `@MainActor` models (`applyMasterBroadcastAndResetPlayers(...)`, `setMapUpdateTypeAndSyncPawns()`, `completeSpaceReveal(itemId:)`). The two task-scheduling blocks (`scheduleSendCharacter`/`scheduleProxyFocus`) each became a small family of `@MainActor` helpers (`schedule...Task()` + `clear...Task(if:)`/`complete...(...)`) so the nil-check/mint-id/assign-task sequence stays one non-interleaved unit, matching the same reasoning.
  - **A genuinely atomic multi-property *read*** (the audit's own explicitly-approved exception, e.g. the `(playerId, masterId)` tuple) — left as `MainActor.run` where it was already correct (`PlayerController.swift:1258,1317,1376`; `MasterController.swift:521,1135`, the latter a derived-boolean read over one delivery-log entry, same category). One new instance of this same class of read (`!hasSendPlayer && !lostMaster`) was instead given a `canSendCharacter` computed property on the model, since a computed property composes with a bare `await` exactly like a method call — no wrapper needed at all, which is strictly better than `MainActor.run` for this shape once the model already exists.
- **Self-correction during the fix:** first attempt at the `Set<UUID>` mutators was one generic pair (`remove(_:from:)`/`insert(_:into:)`) taking a `ReferenceWritableKeyPath<PlayerControllerModel, Set<UUID>>` parameter, to avoid the 8-method duplication below. Failed to compile — "cannot form key path to main actor-isolated property" — Swift disallows forming a key path to an actor-isolated stored property under any circumstances, since a bare `KeyPath` value carries no isolation information itself. Reverted to 8 separate named methods, documented inline for future readers. Also mis-tried `let outgoingCounter = try counter ?? (await gameModel.nextOutgoingMessageCounter())` in `send(...)` (stray `try`, unsafe reliance on async-`??` composition); replaced with an explicit `if let counter { ... } else { ... }`.
- **Verified:** `xcodebuild build` — **BUILD SUCCEEDED** on all 4 platform schemes (iOS Simulator, visionOS Simulator, macOS, tvOS Simulator). `xcodebuild test -scheme MasterRPG -destination 'platform=iOS Simulator,name=iPhone 17 Pro'` — **TEST SUCCEEDED** (21 tests, 9 suites, 0 failures). Post-fix `grep -c "MainActor.run {" PlayerController.swift MasterController.swift` (the `{` excludes prose comments that merely mention the pattern) → 3 and 2 respectively, matching exactly the deliberately-preserved atomic-read sites enumerated above.
- **Severity:** High — resolved.

### 3.2 Same `MainActor.run` anti-pattern replicated across CoreRPG's shared Controllable protocols and several modules' `GameController` — NOW FIXED
- **Location:** `Modules/CoreRPG/Controllable/ImportControllable.swift` (14 sites), `ExportControllable.swift` (9), `GameControllable.swift` (3), `CoreDataSnapshotPersistable.swift` (3 — sits on the CloudKit-remote-change → `ItemController` merge boundary), `SyncDataControllable.swift` (2 — same boundary), `TagController.swift` (1), `SearchControllable.swift` (1); `Modules/{Table,Dice,Weather,Audio}RPG/Controller/GameController.swift` (multiple each); `Modules/GameRPG/Network/ListenerManager.swift` (2), `Modules/GameRPG/Browser/BrowserManager.swift` (2), `Modules/GameRPG/Player/PlayerNetworkController.swift` (1); 3 `GeneratorRPG` AI provider files; `Modules/SpaceRPG/Space/SpaceViewer.swift` (1); `Modules/CharacterRPG/Controller/CharacterPackageVersion.swift` (1).
- **What:** Same root cause as §3.1 (not itself in scope here — left untouched), recurring in the shared protocol default implementations used by every module. `Modules/MapRPG/Controller/GameController.swift` demonstrates the working alternative already used successfully elsewhere in the codebase: every function individually marked `@MainActor`, zero `MainActor.run` calls needed.
- **Why:** The inconsistency across modules increases review burden and the risk of a future edit silently reintroducing an actual race when someone copies the wrong (hop-heavy) pattern instead of the clean one.
- **Fix:** Personally verified `SearchControllable.swift`'s and `SpaceViewer.swift`'s "1 site" each were false positives — a grep-on-the-string artifact from the original audit: both only *mention* `MainActor.run` in a comment explaining why it's *not* used, no actual call. The other ~13 files' real sites (52 total) were each converted using whichever of three patterns actually applied, verified per-site rather than applied mechanically:
  - **Calling an already-`@MainActor` method/initializer** (a *read* or a function call, not a property write) → the `MainActor.run` wrapper is simply redundant; `await` alone hops there (e.g. `await itemControllable.resetModel(with: model)`, `await ItemDataImportModel()`).
  - **A `Task { }` literal written directly inside an already-`@MainActor` function's body** (`TagController.setup`, `ListenerManager`/`BrowserManager`'s `networkTask`) → the whole closure already inherits that isolation; the `MainActor.run` wrapper inside it was dead weight. (`Task.detached`, by contrast, does *not* inherit ambient isolation — confirmed the hard way in `ExportControllable.createExport`, which genuinely needed isolated helper functions.)
  - **A cross-actor property *write*, or multiple statements that need to run as one atomic MainActor unit** — confirmed this is the one case `MainActor.run` (or an equivalent) is structurally required: unlike reads/calls, `await obj.property = value` does not compile for a stored property write from outside the actor (hit and fixed this the hard way in `PdfContentExtractor.swift` — see the correction note below). Extracted a small `@MainActor private func`/mutator method per site instead of keeping the closure-based wrapper, matching `MapRPG/GameController.swift`'s established pattern; several models gained small `set...`/mutator methods (e.g. `PdfContentExtractionResultModel.setPageProgress(_:)`) since a bare `await obj.property = value` isn't valid Swift for a stored-property write.
  Also fixed `Modules/GameRPG/Network/GameNetworkController.swift:786` while confirming no live sites remained outside this item's own location list — that site is actually §3.1's, not §3.2's (an easy mix-up: same anti-pattern, same file directory as the now-fixed `ListenerManager`/`BrowserManager`, but attributed to the `PlayerController`/`MasterController` hot-path finding instead). Fixed it anyway since it was trivial and directly adjacent; noted under §3.1 too so that finding's location list stays accurate.
- **Self-correction during the fix:** first attempted `await resultModel.pageProgress = value` (treating writes like reads) in `PdfContentExtractor.swift`; this doesn't compile — "main actor-isolated property … can not be mutated from a nonisolated context." Property *reads* compose with a bare `await`; property *writes* do not and need an actor-isolated function. Fixed by adding dedicated mutator methods to the 3 `GeneratorRPG` result models instead.
- **Verified:** `xcodebuild build` — **BUILD SUCCEEDED** on all 4 platform schemes (iOS, visionOS, macOS, tvOS). `xcodebuild test` — **TEST SUCCEEDED**.
- **Severity:** Medium — resolved.

### 3.3 `RPGSharePlayController` cannot self-clean on deallocation; relies on callers remembering `reset()` — NOW FIXED
- **Location:** `Modules/GameRPG/SharePlay/RPGSharePlayController.swift:602-685` (class + plain `deinit`), `:1607-1644` (`reset()`); contrast `Modules/GameRPG/Network/ListenerManager.swift:49-53`, `Modules/GameRPG/Browser/BrowserManager.swift:42-44`, `Modules/GameRPG/Table3D/GameTableModel.swift:606-611`, all three of which use `isolated deinit`.
- **What:** `RPGSharePlayController`'s `deinit` was a plain nonisolated `deinit` that only logged, with an in-code comment noting it "cannot access @MainActor-isolated `tasks`." The many session tasks stored in `tasks: [UUID: Task<Void, Never>]` (plus `sendOperationTask`, `deferredPromotionTask`) were only cancelled by an explicit call to `reset()`.
- **Why:** Three sibling files in the same module already solve this with `isolated deinit`. Any future non-singleton instantiation of `RPGSharePlayController` — tests already do this at `Tests/GameRPGTests/SharePlayPackageTransportTests.swift:124,1294` — that's released without calling `reset()` first leaks every task it owns.
- **Fix:** Adopted `isolated deinit`, matching the other three files in this module. Went one step past the audit's literal `{ reset() }` suggestion: `reset()` deliberately leaves `eligibilityTask`/`joinTask`/`modeChangeTask` running (they're lifetime observers documented to survive a session reset, not scoped to it), so a deinit that only called `reset()` would still leak those three. `deinit` now calls `reset()` and separately cancels those three, so every task the instance owns is actually stopped on deallocation, not just the session-scoped ones — with a comment explaining why the extra cancellation is there so it doesn't look redundant with `reset()`.
- **Verified:** `xcodebuild build` — **BUILD SUCCEEDED** on all 4 platform schemes (iOS, visionOS — exercises the `#if os(visionOS)` `modeChangeTask` branch — macOS, tvOS). `xcodebuild test` — **TEST SUCCEEDED**, including `SharePlayPackageTransportTests`, which is exactly where the audit noted multiple non-singleton instances already get created and released.
- **Severity:** Medium — resolved.

### 3.4 `DispatchQueue.main.asyncAfter` used instead of structured concurrency
- **Location:** `Modules/CoreRPG/Navigator/Core/NavigationSend.swift:107-114`, violation at line 112, inside `@MainActor internal func resume(...)`.
- **What:** `DispatchQueue.main.asyncAfter(deadline: .now() + delay) { self.send(values: values) }` implements a delayed navigation resume via old-style GCD.
- **Why:** Directly violates the project's explicit house rule ("never use `DispatchQueue.main.async()`-style GCD; always use modern Swift concurrency") and, more importantly, is unstructured and uncancellable — a delayed navigation resume can fire after the navigator/view it targets is already gone. A full repo sweep found exactly 2 other `DispatchQueue` uses, both legitimate Network.framework/`NWConnection` interop with no async-native equivalent (`ConnectionController.swift:31`, `NWParameter+GameMaster.swift:13`) — this is the one clear non-test survivor.
- **Action:** Replace with a tracked `Task { try? await Task.sleep(for: .seconds(delay)); await send(values: values) }`.
- **Severity:** High

### 3.5 Fire-and-forget `Task` inside `.onAppear` instead of the `.task` modifier — NOW FIXED
- **Location:** `Modules/GameRPG/SetupViews/SelectedMasterView.swift:32-38`; `Modules/SpaceRPG/Record/TutorialVideoView.swift:47-62`.
- **What:** Both views spawned `Task { @MainActor in try? await Task.sleep(for: ...); <mutate state> }` from `.onAppear` rather than using the `.task { }` view modifier.
- **Why:** `.onAppear`-spawned tasks aren't tied to the view's lifetime and were never cancelled if the view disappeared before the sleep completed (2s in `SelectedMasterView`, up to 4s in `TutorialVideoView`) — a dismissed view could still mutate `root.gameModel.selectedGameMaster`/`appModel.orbitState` afterward.
- **Fix:** Both replaced `.onAppear { Task { ... } }` with `.task { ... }`, matching the pattern already used by `SelectedMasterView`'s sibling views (`SelectedAdventureView`, `SelectedPlayerView`), which needed no explicit `@MainActor` — a `.task` closure already inherits the view's isolation. `TutorialVideoView` had two independent `Task`s inside one `.onAppear` (one unconditional, one gated on `!isInReviewSheet`); since `.task` only carries one async operation, it became two separate `.task { }` modifiers on the same view, run concurrently exactly as before. Also fixed a related latent bug while doing this: `try? await Task.sleep(for:)` swallows `CancellationError` into `nil` and execution continued past it either way — added an explicit `guard !Task.isCancelled else { return }` after each sleep in both files, so a mid-sleep cancellation actually stops the mutation instead of just being caught and ignored.
- **Verified:** `xcodebuild build` — **BUILD SUCCEEDED** on the iOS Simulator destination and on `generic/platform=iOS` (`TutorialVideoView.swift` only compiles for a real device — `!targetEnvironment(simulator)` — so the simulator build alone doesn't touch it; see §4.3 for why `generic/platform=iOS` is the right destination for that).
- **Severity:** Medium — resolved.

### 3.6 `CoreDataChangeObserver`'s `@unchecked Sendable` rests on an unenforced single-call-per-instance assumption — NOW FIXED
- **Location:** `Modules/CoreRPG/Persistence/CoreDataChangeObserver.swift:14-46`.
- **What:** `private var observer: AnyCancellable?` is mutable state inside a `@unchecked Sendable public final class`. The file's own comment (lines 8-12) documented *why the class can't be `@MainActor`* (Core Data posts change notifications synchronously on the context's own possibly-background queue) but not the actual soundness precondition: safety depends entirely on `observeCoreDataChanges` being called exactly once per instance. The 12 real call sites (one per module's `SyncDataController.init`) do satisfy this, but nothing in the type enforced it.
- **Why:** An undocumented invariant is one refactor away from becoming a real race — a future call site that reuses an existing `CoreDataChangeObserver` instance for a second `observeCoreDataChanges` call would silently drop the first subscription's cancellable, with no compiler signal.
- **Fix:** Did both of the audit's options rather than choosing one: added a doc comment on the class right next to the existing `@unchecked Sendable`/`@MainActor` rationale, explaining the single-call precondition and pointing at where it's already satisfied (`SyncDataControllable.startSyncObservation`, added in §9.2's fix); and added `precondition(observer == nil, ...)` at the top of `observeCoreDataChanges` so a future violation traps immediately with a clear message instead of silently dropping the first subscription.
- **Verified:** `xcodebuild build` — **BUILD SUCCEEDED**; the precondition doesn't change behavior for any of the 12 existing (correct) call sites.
- **Severity:** Medium — resolved.

### 3.11 Closure-based `NotificationCenter.addObserver` where an async notification sequence is available — NOW FIXED

### 6.1 Hardcoded, world-shared TLS pre-shared key allows any local device to join or inject state into any game
- **Location:** `Modules/GameRPG/Network/GameSecurity.swift:7` (`static let passcode = "GameMasterCode"`); `Modules/GameRPG/Network/NWParameter+GameMaster.swift:21,27-61` (used to build TLS parameters for both `NWListener` and `NWConnection`); `Modules/GameRPG/Network/ListenerManager.swift:124`; `Modules/GameRPG/Browser/BrowserManager.swift:52-135`; `Modules/GameRPG/Controller/MasterController.swift:185-215` (`add`/`accepts(connectionId:sender:)`), `:835-895` (`accepts(_:origin:)`).
